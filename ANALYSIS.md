# Разбор исходного проекта и карта переноса

## Исходная архитектура

LamoFrame — не только редактор лендингов. Django-приложение `builder` объединяет
визуальный конструктор и построение приложений на коллекциях данных.
В репозитории около 10 000 строк клиентских ES-модулей и около 2 000 строк
серверной логики и тестов. Кроме кода изучены маршруты, формы, миграции,
шаблоны, фикстуры, настройки, Docker, README и материалы MD.

| Слой | Назначение | Перенос |
| --- | --- | --- |
| `models.py`, миграции | 10 предметных моделей плюс пользователь | SQL-схема `lib/db.mjs`, JSONB и внешние ключи |
| `views.py` | Аккаунты, проекты, файлы, экспорт, публичное превью | `lib/server.mjs`, `lib/auth.mjs` |
| `application.py` | Схемы, связи, валидация записей, привязки | `lib/collections.mjs`, `lib/document.mjs` |
| `application_views.py` | Управление, публикация, роли и приглашения | `lib/server.mjs` |
| `adapters.py`, allauth | Google OAuth и коллизии аккаунтов | `lib/oauth.mjs` |
| `business.py`, fixtures | Шаблоны и B2B-аналитика | `data/*.json`, таблица `templates` |
| Django Templates | Русскоязычный интерфейс | `templates/`, Nunjucks с экранированием |
| `admin.py` | Управление проектами, файлами и шаблонами | `lib/admin.mjs`, `/admin/` |
| `seed_demo` | Демо и администратор | `scripts/seed-demo.mjs` |
| WhiteNoise, gunicorn, middleware | HTTP, статика, заголовки | Next.js, `public/static`, Docker |

## Редактор

`state.js` содержит документ, историю, выделение, страницы, фреймы, группы,
компоненты и создание адаптивных макетов. `canvas.js` отвечает за перемещение,
масштабирование, панорамирование и рисование. `selection.js`, `snapping.js`,
`layers.js`, `pages.js` и `panels.js` обеспечивают управление объектами и их
свойствами. `blocks.js` содержит библиотеку блоков.

`render.js` — общий рендерер редактора, предпросмотра и экспорта, включая
динамические графики, KPI, таблицы, навигацию, калькуляторы и формы записей.
`bundle.js` собирает многостраничный сайт с изображениями, `zip.js` формирует
ZIP. `editor.js` связывает модули, выполняет автосохранение, запускает превью
и экспорт. `application.js` получает опубликованный документ и живые записи,
затем рисует рабочее приложение в sandbox iframe.

Эти модули и ресурсы перенесены целиком в `public/static`. Это сохраняет
возможности холста и автономного экспорта. Next.js обслуживает серверную часть,
а Nunjucks заменяет Django Templates без зависимости от Python в runtime.
При замене шаблонизатора отдельно учтено различие проверки пустых массивов
и объектов: оно влияет на пустой дашборд и кнопки экспорта приложений.

## Модель и поведение

Документ JSON версии 3 содержит метаданные, настройки, страницы, фреймы,
компоненты и макеты устройств. Совместимость с версиями 1–2 оставлена в
клиентской миграции. Сервер ограничивает размер документа 8 МБ, экспорт 12 МБ,
число страниц 50, фреймов 400, элементов 5000, глубину 40.

Проект принадлежит одному владельцу. Доступ к чужим проектам редактора даёт
404. Сохранение проверяет `base_updated_at` атомарно в UPDATE; конфликт даёт
409. Изображения проверяются по содержимому, до 2 МБ, максимум 200 на проект.
При дублировании копируются медиа и переписываются ссылки.

Рабочие приложения используют коллекции, поля text/number/date/status/relation
и записи JSONB. Лимиты: 15 коллекций, 20 полей, 200 записей. Обязательное поле
нельзя добавлять в коллекцию с записями или опубликованной схемой. Публикация
фиксирует сохранённый документ и схемы привязанных коллекций. Записи остаются
живыми. Editor меняет записи, viewer только просматривает. Владелец управляет
схемой, публикацией и участниками. Дубликат переносит схему и перепривязывает
ID коллекций/полей, не копируя записи, публикацию и доступ участников.

## Безопасность и эксплуатация

SQL использует параметры. Пароли новых пользователей хешируются scrypt;
поддерживается проверка Django PBKDF2-SHA256 при импорте. Сессионные токены
случайные, в базе хранится SHA-256 токена, cookie HttpOnly и SameSite=Lax.
Изменяющие запросы проверяют CSRF и Origin. Публичный HTML получает sandbox CSP,
чтобы пользовательский JavaScript не читал сессию сервиса. Формы и HTML-данные
экранируются; JSON в script защищён от закрывающего тега script.

PGlite — встроенный PostgreSQL на файловом диске. Он сохраняет транзакции,
JSONB, уникальные индексы и каскадное удаление без отдельного сервера БД.
Одна папка базы должна принадлежать одному процессу. Это подходит исходному
локальному/учебному приложению; несколько реплик требуют PostgreSQL-сервера.

Django admin заменён собственной админкой. Служебные страницы Django/allauth,
которые не входят в интерфейс продукта (например, внутренние формы провайдеров),
не воспроизводятся как страницы Django. Вход Google перенесён самостоятельным
OAuth-потоком. Отправка писем для восстановления пароля в исходном интерфейсе
не была настроена и в перенос не добавлялась.

## Проверка переноса

Серверные интеграционные тесты используют настоящую временную PGlite-базу.
Проверяются аккаунты/CSRF, страницы, владение, документы, конфликты сохранения,
изображения, независимое копирование файлов, публикация, приглашения, роли,
изоляция черновика и валидация связей/статусов/дат.

Браузерный сценарий проверяет регистрацию, пустой дашборд, выбор B2B-шаблона,
открытие холста, автосохранение, перезагрузку, скачивание ZIP, коллекцию,
обязательное поле и создание записи. Production-сборка проверяется отдельно.
Google OAuth требует внешней настройки и не проверялся реальным входом.

## Улучшения сохранения и жизненного цикла проекта

Сохранение JSON отделено от HTML. Публичные сайты переведены на `site_publications`:
публикация фиксирует HTML, название и версию источника. Обновление черновика
не меняет публичный снимок. HTML генерируется серверным общим рендерером,
внутренние изображения встраиваются без внешних серверных запросов.

`project_versions` хранит автоматические и именованные снимки холста.
Сохранение и создание страховочной версии происходят в одной транзакции;
восстановление проверяет версию черновика. Нумерованные миграции применяются
однократно и не переписывают старые проекты.

`local-drafts.js` сохраняет копии в IndexedDB по аккаунту, проекту и вкладке.
`project-safety.js` управляет восстановлением, конфликтами, историей и публикацией.
Сравнение локальных и серверных документов учитывает перестановку ключей JSONB.
`project-checks.js` проверяет геометрию и незаполненные элементы, позволяет
перейти к замечанию из панели адаптива.

Непредвиденные серверные ошибки больше не отдают внутренние сообщения клиенту:
API получает безопасный JSON, страничные запросы — HTML с сообщением и ссылкой
на список проектов. Технические ошибки остаются в серверном журнале.

## Конструктор CRM, общий sidebar и темы

`lib/crm-template.mjs` создаёт пять страниц, схему четырёх коллекций, настоящие
связи и необязательные демо-записи одной транзакцией. Символьные ключи
шаблона заменяются ID созданных коллекций/полей. Дублирование проекта
перепривязывает поля аналитики и канбана, не копируя записи и доступ.

`crm-widgets.js` добавляет канбан, вычисление показателей и группировку
диаграмм, поиск/сортировку/фильтры таблиц и выбор периода. Элементы являются
частью обычного документа конструктора, их привязки редактируются в панели.
Общий renderer используется в холсте, превью, рабочем приложении и экспорте.

Рабочее приложение остаётся в sandbox iframe. Сообщения проверяются по
source и опубликованной коллекции. Изменения отправляет родительский документ
с CSRF, а `lib/crm-actions.mjs` повторно проверяет актуальную роль,
опубликованную схему, связи, статус и версию записи. Удаление защищает
входящие связи. Миграция 2 вводит `records.revision` и `record_events`.
Карточки показывают комментарии, события, связанные записи и действия.

`site-shell.js` создаёт одну навигационную панель с автоматическими ссылками
на страницы, ресайзом, сворачиванием и мобильным меню. `site-settings.js`
разделяет авторские настройки сайта и настройки редактора. Ширина sidebar
уменьшает доступную ширину секций. Режим потока CRM использует CSS grid;
свободные макеты сохраняют координаты и масштабируются под оставшееся место.

Тема light/dark/switchable сохраняется в документе. Предпочтения посетителя
хранятся отдельно; sandbox отправляет их родителю вместо доступа к storage
из iframe. Генераторы автономного HTML и многофайлового ZIP включают
те же стили и скрипты sidebar/тем. Переходы между страницами внутри Blob
переключают DOM без навигации по недоступному Blob URL.

## Текущий режим: PGlite в браузере

Production-маршрут `app/[[...path]]/route.js` больше не импортирует серверный
обработчик или файловую PGlite: он возвращает только `browser-shell.mjs`.
Формы, HTTP-подобные вызовы редактора и рендеринг страниц выполняются в
`browser/bootstrap.mjs`/`browser/backend.mjs` на устройстве посетителя.

Сборка esbuild подставляет браузерные адаптеры базы, шаблонов, изображений и
локального профиля в общую предметную логику. Чтение подготовленных шаблонов
и фикстур происходит из сборки; медиа хранятся в `local_files` как BYTEA.
PGlite работает в одном SharedWorker c `idb://` VFS. Соединения вкладок
обслуживаются через MessagePort, транзакции закрепляются за вкладкой.
Жизненный цикл вкладки отслеживается Web Lock, который освобождается браузером
при закрытии или сбое: незавершённая транзакция откатывается автоматически.
Ни формы, ни SQL, ни изображения не требуют записи в файловую систему Vercel.

Навигация использует обычные URL Next.js, а загрузившаяся оболочка отображает
локальную страницу. Каждый полный переход создаёт новый модульный контекст
редактора; multi-tab worker сохраняет согласованный доступ к базе между
вкладками и переходами. Локальные операции дополнительно сериализуются Web Locks.

Профили не защищены паролем. Google OAuth, приглашения, общая серверная админка
и совместный доступ отключены в браузерной сборке. Снимки публикации локальные.
HTML пользовательского превью по-прежнему помещается в sandbox iframe.

`browser/backup.mjs` переносит все локальные таблицы и медиа в JSON, проверяет
структуру и восстанавливает их одной SQL-транзакцией. Неверная копия откатывается.
`export-browser.mjs` конвертирует прежнюю файловую PGlite в тот же формат без
публикации пользовательских данных в статических ресурсах.

Ранние разделы этого документа описывают историю серверного переноса;
текущая production-архитектура — браузерная, как описано в этом разделе.
